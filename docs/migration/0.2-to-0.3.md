# Migrating from 0.2.x to 0.3.0

0.3.0 is the **production-readiness and multi-tenancy** release. Unlike 0.2.0, it
is **not** a wire-contract break: a 0.2.x OTLP producer keeps working unchanged.
The only thing that changes for an existing deployment is the **on-disk layout**,
and that migration happens **automatically** on first start. Everything else —
authentication, TLS, retention, snapshots, multi-tenancy — is **opt-in** and off by
default, so an upgrade with no config changes behaves exactly as 0.2.x did, just
with the operational endpoints added.

## What is and isn't affected

| Area | Impact |
| --- | --- |
| **OTLP producers** (what an agent emits) | **None** — the entity-event wire contract is unchanged from 0.2.0. |
| **GraphQL / MCP consumers** | **None** — schemas and tools are unchanged. A query may now carry an optional `X-Scope-OrgID` header (see [Multi-tenancy](#multi-tenancy)); without it, you read the `default` tenant. |
| **Stored event log** (the data dir) | **Layout change, auto-migrated.** State moves from `<data-dir>/` to `<data-dir>/<tenant>/`; a pre-existing store is relocated under `<data-dir>/default/` on first start. **No event-format change** — the events themselves are read as-is. |
| **`toise-server` flags / config** | **Additive** — existing flags keep their names and defaults; the new auth/TLS/hardening/retention/snapshot settings are all opt-in. |
| **`toise-probe`** | The bundled probe now emits `connected_to` topology relations instead of the legacy `adjacent_to`. Only relevant if you run `toise-probe` itself. |

## 1. The data-dir layout change (the one thing to know)

Before upgrading, **take a backup of your data directory** (or use
`Store.Checkpoint` / the documented backup step). On first start, 0.3.0 detects a
0.2.x single-tenant data directory — a Pebble store written directly under
`<data-dir>/` — and relocates it under `<data-dir>/default/`:

```text
# before (0.2.x)                 # after first 0.3.0 start
<data-dir>/                       <data-dir>/
  CURRENT                           default/
  MANIFEST-000001                     CURRENT
  000005.sst                          MANIFEST-000001
  ...                                 000005.sst
                                      ...
```

This is one-way and idempotent: once migrated, subsequent starts see the
per-tenant layout and do nothing. If you roll back to 0.2.x, point it at
`<data-dir>/default/` (or move the files back to the root).

No action is required beyond the backup — but if you provision the data directory
with infrastructure-as-code, expect the new `default/` subdirectory.

## 2. Enabling authentication and TLS (opt-in)

Off by default (the server still binds to loopback). To require bearer tokens on
the ingest and query surfaces, supply them via the environment:

```bash
export TOISE_AUTH_TOKENS="token-a,token-b"
```

To serve the HTTP surfaces over TLS, point at a certificate and key
(`tls_cert_file` / `tls_key_file`, or the matching `TOISE_*` env / flags). The
operational probes (`/healthz`, `/readyz`) and the metrics scrape (`/metrics`) stay
public so a load balancer and Prometheus can reach them without a token. See
[Authentication & TLS](../operations/configuration.md#authentication--tls).

## 3. Locking down for production

A single switch removes the development affordances:

```bash
toise-server --production            # or TOISE_PRODUCTION=true
```

`--production` turns off GraphQL introspection, the `/playground`, and the debug
UI in one move; `allowed_origins` gates browser WebSocket origins. Each lever is
also individually configurable if you want a different mix. See
[Hardening for production](../operations/configuration.md#hardening-for-production).

## 4. Bounding disk and speeding restarts (opt-in)

- **Retention** — set `retention_max_age` (e.g. `720h`) to prune events past the
  horizon while preserving current state. Mind the
  [`asKnownAt` caveat](../operations/configuration.md#retention--bounding-on-disk-growth):
  keep the horizon longer than the deepest audit you need.
- **Snapshots** — set `snapshot_interval` (e.g. `5m`) so restart time is bounded by
  snapshot age, not total history.

## 5. Operational endpoints

New in 0.3.0 and always on: `/healthz` (liveness), `/readyz` (readiness — green
only when every tenant store is healthy), and Prometheus `/metrics`. Wire these
into your orchestrator and scrape config. Logs are structured; set the verbosity
with `--log-level`.

## Multi-tenancy

One Toise instance can now serve multiple tenants with **fully isolated** graphs.
This is **opt-in and transparent**: if you never set a tenant id, everything lives
under `default` and behaves as a single-graph deployment. To use it, have the
upstream OTel Collector stamp each client's stream with an `X-Scope-OrgID` (gRPC
metadata on ingest) or a `tenant.id` resource attribute, and pass `X-Scope-OrgID`
on query requests. Full details and the security caveat (auth is not yet bound to a
tenant) are in [Multi-tenancy](../operations/configuration.md#multi-tenancy).

## Upgrade checklist

1. **Back up** the data directory.
2. Deploy the 0.3.0 binary / image; start it. The data dir migrates to
   `default/` automatically — check the startup log line `migrated legacy
   single-tenant data dir to default tenant`.
3. Confirm `/readyz` is green and `/metrics` scrapes.
4. (Optional) Set `TOISE_AUTH_TOKENS`, TLS, and `--production` for an exposed
   deployment.
5. (Optional) Set `retention_max_age` and `snapshot_interval`.
6. (Optional) Configure `X-Scope-OrgID` in the upstream Collector for
   multi-tenancy.
