# Migrating from v0.8.0 to v0.9.0

v0.9.0 aligns Toise more strictly with the OpenTelemetry entity-events spec (1.58.0)
and lets you decouple ingest authentication from read authentication. It is **not** a
wire-contract break and there is **no data migration**. Everything new is **additive**
and, where it changes a posture, **opt-in** — upgrade in place, change nothing, and the
server behaves exactly as it did on 0.8.0. Reach for the new features only when you need
them.

## What is and isn't affected

| Area | Impact |
| --- | --- |
| **Operators / auth** | **None required.** The new `ingest_mtls_only` (`TOISE_INGEST_MTLS_ONLY`) is **off by default**; the existing bearer-on-ingest posture is unchanged. Turn it on only to authenticate OTLP ingest by mutual TLS alone while keeping read-surface tokens — it requires `tls_client_ca_file`. See the [configuration reference](../user-guide/docs/configuration.md). |
| **MCP consumers** | **None required.** `recent_changes` / `graph_diff` may now include an `entity.delete.reason` on delete events (additive field); entity descriptions may now include array / nested-map values rendered as compact JSON tagged `array` / `kvlist`. Existing calls are unchanged. |
| **GraphQL consumers** | **None required.** `ChangeEvent` gains an optional `deleteReason` field. No change to existing queries or types. |
| **OTLP producers** | **None required.** Two optional capabilities are now *accepted*, not demanded: a richer `entity.description` (full `AnyValue` — arrays and nested maps, not just scalars) and an optional `entity.delete.reason` on `entity.delete`. **Identity is unchanged — `entity.id` must stay flat scalars** (ADR 0018). |
| **Liveness semantics** | **Clarified, not changed.** `entity.report.interval == 0` (or absent) means **no cadence**: the entity is removed only by an explicit `entity.delete`, never by the liveness sweep. This is now locked by a conformance test — behaviour is the same as before, just contractually pinned. |
| **Stored data** (the data dir) | **No migration on upgrade.** Existing event logs, snapshots, and shipped segments are read as-is; the richer description values and the delete reason are additive fields. A downgrade ignores them. |
| **Release tags** | `v0.9.0` (server) and **`pkg/emit/v0.3.0`** (SDK). If you emit with the SDK and want the new fidelity, upgrade to `pkg/emit/v0.3.0`; scalar-only producers on `v0.2.0` keep working unchanged. Assets and the GHCR image carry the tag verbatim (`toise_v0.9.0_linux_amd64.tar.gz`, `ghcr.io/toise-dev/toise:v0.9.0`); docs URLs keep the unprefixed style (`/docs/0.9.0`). |

## Adopting the new features (optional)

- **Richer descriptions:** emit arrays / nested maps in `entity.description` — with the
  SDK, `Entity.RichAttributes` (`map[string]any`). Keep `entity.id` flat scalars.
- **Delete reasons:** set `entity.delete.reason` on a delete (SDK: `Entity.DeleteReason`)
  to record *why* an entity went away; it surfaces on the change feeds.
- **mTLS-only ingest:** when producers already authenticate by client certificate
  (`tls_client_ca_file`), set `ingest_mtls_only` so OTLP ingest needs no bearer while the
  read surfaces keep their scoped tokens / OIDC.

Each is independent. The [configuration reference](../user-guide/docs/configuration.md)
lists every key; the [ingestion guide](../user-guide/docs/ingestion.md) documents the
wire contract.

## The one thing to check: identity is still scalar

The wider `AnyValue` support is for **descriptions only**. `entity.id` (and
relation-endpoint ids) must remain flat maps of scalars — exact-match identity is over
scalar strings (ADR 0018). A nested value in an identity map is dropped and surfaced
(a `Warn` naming the key), never hashed. If you were pre-flattening identity with dotted
keys (`{"server.address": "10.0.0.1"}`), keep doing exactly that; only descriptive
attributes gained the freedom to nest.
